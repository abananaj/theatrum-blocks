The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Breaking:** `theatrum/card-expanding` and `theatrum/card-expand-overlay` are both retired and replaced by a single new `theatrum/card-expand`, which picks between their two reveal mechanics via a new **Reveal Style** Inspector control (`revealStyle`: `expand` default / `overlay`). There is no automatic migration for the rename — a card's own saved shapes (from the block-name change or from either predecessor's `deprecated.js` history) are not read by the new block name — so **existing `theatrum/card-expanding` content must be manually recreated with `theatrum/card-expand`** (one known published page uses it). **Expand** (default) is `theatrum/card-expanding`'s behaviour with one correction: the body opens beneath a heading that stays put, but it is absolutely positioned at `top: 100%` once `.is-ready`, so the card keeps the footprint it has closed — image plus header — and the opening body hangs below it over whatever follows instead of growing the card and shifting the rest of the page down (`.is-expanded`'s existing `z-index` lifts it over what it covers). It is out of flow in both states, not only while open, so closing animates the way opening did rather than snapping back into flow first; the card can no longer clip its own children, so `__image` carries the top corner radii itself and the panel repeats the card's background, bottom radii and shadow. `view.js` now *wraps* the body group in the `__collapse` element rather than tagging the group itself, because the group carries the theme's padding and a padded box can't collapse to nothing — `height: 0` leaves the padding behind, which out of flow would hang below every closed card as a strip of background with the body's first line showing through it. The nested content is seeded as two `core/group`s — **Card header** (holds the heading `view.js` turns into the accessible trigger, or, with no heading, the whole group stands in for it) and **Card body** (what opens) — found by class rather than position, with `view.js` falling back to a first-heading-then-everything-after heuristic for a flat pre-split shape. **Overlay** reworks `theatrum/card-expand-overlay`'s behaviour: closed, the card is indistinguishable from an Expand one — the image, with the header below it — and opening it slides the header and body up over the image as one panel, coming to rest on the card's bottom edge with whatever the image is taller than the panel still showing above. Image and content share one `__frame`, which needs no sizing of its own: the image gives it its height in normal flow, and `style.scss` pads a header-tall strip underneath it (`padding-block-end: var(--theatrum-card-expand-header-height)`) for the closed header to sit in — `view.js` measures that variable, since the header is whatever blocks the author put there at whatever width they wrap to, and keeps it current with a `ResizeObserver` (a rewrapped heading, a late web font). Once `.is-ready`, `__content` is absolutely positioned with its top edge at the frame's bottom (`top: 100%`, which resolves against the padding box, clearing the strip) and pulled back by exactly the header's height; opening translates it to `-100%` — 100% of the *panel's own* box, not the frame's, which is what lands the body flush with the card's bottom rather than blanketing the image. `max-height: 100%` keeps a tall panel inside the frame (a percentage that resolves because an absolutely positioned box's containing block always has a used height), `__header` stays fixed at the panel's top and `__body` scrolls its own overflow, so a body with more to show than the frame has room for never pushes the panel past the top of the card. The whole `__frame` becomes the accessible trigger (`role="button"`, keyboard-activatable, `aria-expanded`/`aria-controls`) since the header travels with the body rather than staying put, with an `aria-label` borrowed from the header's own text; `aria-hidden` goes on `__body` alone, because the header is on show in both states. In both modes the header and body overlap by a hairline (`margin-block-start: -1px`): the two sections meet at whatever fractional height the header's content works out to, and a boundary that lands mid-device-pixel is antialiased, so both backgrounds blend with the block's own light backing behind them (`__content` in Overlay, the `__collapse` wrapper in Expand) and a card whose sections an author has painted darker than the card shows a faint light line between them. Expand mode needs `z-index: 1` on `__header` as well, since its out-of-flow panel otherwise paints its backing between the two. Both modes click-delegate to the whole card (except real interactive descendants), warn in the Inspector when the header has nothing to trigger with, and gate their JS-only markup behind `.is-ready` so a non-JS visitor gets a complete, ungated card; an open card of either mode also collapses when a click lands outside it, which one shared `document` listener over a registry of per-card collapse callbacks handles (the pattern `theatrum/popover` uses, hoisted to a single listener), so a click on a sibling card closes the first and only one card is ever open at a time. A second, independent **Activate On** control (`activateOn`: `click` default / `hover`, a wrapper class `is-hover`) picks what triggers either mechanic. **Hover** reveals the card while the pointer is over it and hides it when the pointer leaves, with `focusin`/`focusout` giving the keyboard the same reveal (`relatedTarget` checked against the card, so moving focus within it doesn't close it) — and it deliberately builds no trigger and sets no ARIA at all: no `<button>`, no `role="button"`, no `aria-expanded`, no `aria-hidden`, because there is nothing a visitor can press and the content simply stays in the accessibility tree while the reveal is purely visual. Everything structural still runs either way, since that is what the CSS animates. Hover doesn't exist on a touch screen, so `view.js` gates it on `matchMedia( '(hover: hover)' )` and falls back to the complete Click-mode wiring where it doesn't match — a hover card on a phone is a tap-to-open card, not an unreachable one, which is also why nothing in `style.scss` keys off `is-hover`. Hover mode alone offers **Link the image to the post** (`linkImageToPost`), since with no click needed to open the card a click has nothing else to do and a keyboard visitor otherwise has no tab stop on the card at all: `theatrum_card_image_html()` gained optional `$link_url`/`$link_label` parameters (`theatrum/card-scroll`, its other caller, is unaffected by the defaults) and wraps the picture in an `__image-link` anchor *inside* `__image`, so the geometry custom properties stay on the element every stylesheet targets and the `__image img` rules reach through it; `render.php` supplies `get_permalink()` for the post being rendered — each queried post in turn inside a Query Loop — and `get_the_title()` as an `aria-label`, since a featured image's alt text belongs to someone else's post and a decorative one has none. Shares `src/components/card-image`'s controls, hiding Width and restricting Height to absolute units in Overlay mode (`showWidth`/`heightUnits` props on `CardImageControls`) since the image always fills the frame edge-to-edge there
- An Icon Accordion no longer yanks the page when a card opens. It runs with `autoclose` on, so a click usually collapses one card and opens another; when the card that closes sits above the one you clicked, the page loses that height while the scroll position stays put and the heading you were aiming at slides up under the cursor. `src/accordion-icon/view.js` measures the clicked toggle in the capture phase, before core's Interactivity API store flips the card, then holds it at that viewport position for the length of the card's own transition — read from the computed style, so it tracks whatever `--ct-duration-slow-1` resolves to and collapses to nothing under `prefers-reduced-motion`. It runs as a closed loop, re-measuring and correcting each frame rather than computing one offset up front, so it converges while the `0fr` -> `1fr` row is still animating and cannot run away if the browser's own scroll anchoring adjusts too; a wheel, touch or key event hands control straight back to the reader. Registered on `init` and enqueued by a `render_block` sniff for `core/accordion` carrying the style class — the same enqueue-only pattern `inc/format-controls.php` uses — so it loads for the accordions that need it and nowhere else, and it is a pure enhancement: without it the accordion behaves exactly as before
- Each card of an Icon Accordion gained an **Icon** inspector panel — a media-library picker for the rail icon and a palette for the rail's background colour. It is a `ToolsPanel`, and the rail colour is deliberately _not_ `isShownByDefault` — the exception to this codebase's usual preference, because the rail is meant to read as a tinted strip of the card and colouring it separately is the deliberate case rather than the common one; it is one menu item away, and stays visible once set. `src/accordion-icon/controls.js` extends `core/accordion-item` through the same `registerBlockType`/`BlockEdit`/`BlockListBlock`/`getSaveContent.extraProps` filters `src/format-controls.js` uses, and the panel only appears inside an accordion carrying `is-style-tm-accordion-icon`, so it reads the parent block rather than its own attributes. Both settings persist as custom properties in the card's inline style (`--tm-accordion-icon-glyph`, `--tm-accordion-icon-rail-bg`), since a class cannot carry an arbitrary URL or colour, with a `has-ct-icon` marker class beside them for the CSS to key off. Two KSES details govern the values written: an attachment URL survives because a `--*` property whose value starts with `url(` is protocol-checked against `wp_allowed_protocols()` and then lifted out of the string before `safecss_filter_attr()`'s "no bare parentheses" test (a `data:` URI would not survive, which is why the retired built-in glyph set could never have come from the panel); and a palette choice is stored as `var(--wp--preset--color--<slug>)` rather than the literal colour, because only `var`/`calc`/`clamp`/… are lifted out before that same test, so a literal `hsl(...)` — what most of this theme's palette resolves to — would be silently dropped for anyone without `unfiltered_html`; storing the preset var also means a repalette follows automatically. The icon is painted on the toggle-icon span itself rather than on a `::after`: a pseudo-element is a second grid item beside the anonymous one holding the suppressed `+`, and with `align-content` defaulting to stretch the two auto rows split the box evenly, centring the icon in the lower half — ~18px below the title, with a visible gap above it. The icon is drawn as a `background-image` rather than masked in the card's text colour: this site offloads its media to S3, CSS `mask-image` is CORS-restricted where `background-image` is not, and the bucket sends no `Access-Control-Allow-Origin`, so a masked attachment paints nothing at all with no error anywhere. The built stylesheet is now also enqueued on `enqueue_block_editor_assets` so the panel's preview swatch can draw its image exactly as the rail does — the editor canvas is an iframe and the inspector is not inside it
- An Icon Accordion now colours itself from the nomenclature ramp by card position — primary, secondary, tertiary, quaternary, quinary, then muted-light for the sixth card and every one after it — each paired with the `--ct-on-*` text colour the nomenclature recipes compute to be legible on it. The rules read the semantic `--ct-*` layer rather than fixed presets, so a stack retints inside any `.is-nomenclature-*` context, is coloured the moment it is inserted, and keeps colouring itself as an author adds cards. Guarded on `:not(.has-background)` so an author's own choice still wins, and it removes the need for `is-text-dark` on cards left on the ramp — that class stays for cards painted a light colour by hand, since `core/accordion-item` supports `color.background` but not `color.text` at any level of the family. The rail follows the same principle: left unset it is `color-mix(in srgb, currentcolor 12%, transparent)` — a flat strip mixed from whatever text colour the card carries, so it lightens a dark rung and darkens a pale one — rather than the fixed black-and-white gradient overlay it started as, which had to be re-tuned by hand for every surface. A colour chosen in the Icon panel replaces that tint outright instead of sitting under an overlay, so the rail is exactly the colour the author picked
- **Icon Accordion** — a `core/accordion` variation plus matching block style (`is-style-tm-accordion-icon`), modelled on the "responsive expandable cards table" CodePen in `.examples/`: a stack of full-bleed coloured cards, each with an icon rail, expanding in place. Ships as `src/accordion-icon/` (a `registerBlockVariation` entry plus the stylesheet) with a new webpack entry; `theatrum-blocks.php` registers the style, enqueues the editor script, and attaches the CSS with `wp_enqueue_block_style('core/accordion', …)` — the plugin's first use of that API, which loads the stylesheet only on pages that actually render an accordion, so no `render_block` class sniff is needed. None of the CodePen's markup survives: core supplies the button semantics, `aria-expanded`/`-controls` and `hidden="until-found"` panels (so Ctrl-F finds text inside a collapsed card, which the CodePen's `tabindex`/`onfocus` version could not do), and the variation supplies only the look. Two deliberate departures from the model — collapsed cards show no truncated body copy, since core renders a closed panel with `content-visibility: hidden` and there is nothing left to clip behind the CodePen's bottom-edge gradient mask, which is therefore not reproduced at all; and the fixed container height is replaced by fixed collapsed rows plus a natural-height open card, so a long panel can never be clipped. Open/close animates the panel's grid row `0fr` -> `1fr`, the hook core's own accordion-item stylesheet anticipates. The fallback `+` — shown until a card is given an icon — is drawn dark on every card (`--tm-accordion-icon-plus-color`) rather than in the card's own text colour, so it reads as the accordion's control rather than as part of the card's copy; on the two darkest rungs that is low contrast by design. It keeps core's own 45°-into-× rotation on open, but a card carrying a media icon gets a scale instead (`--tm-accordion-icon-glyph-open-scale: 1.15`, `style.scss`): a rotating ticket or spotlight reads as a glitch, and the `.has-ct-icon.is-open` selector is one class heavier than core's own `.is-open` rule so it wins outright rather than depending on this stylesheet loading after core's, which happened to be true but was never guaranteed. Both glyphs share the same transition (`--ct-duration-fast-1`/`--ct-ease-standard`), so switching between them is one motion vocabulary rather than two. A collapsed card measures exactly `--tm-accordion-icon-row`: the panel's closing space is a margin on its last child, not padding on the panel, because `min-height: 0` and `overflow: hidden` take the panel's minimum contribution to zero but padding sits outside the content box and survives that — as padding it kept every closed row 24px taller than declared, with the title and rail glyph riding 12px above the card's centre. Per-card icons come from the media library through the Icon panel, and card colours from the nomenclature ramp by position — both described in their own entries above. The style's foreground/heading/panel resets are load-bearing, not tidying — `chance-ollie` paints the heading `--ct-primary` and the panel `--ct-light` from theme.json, which would otherwise cover every card colour. The rail glyph is anchored to the heading and pulled back one rail-width rather than anchored to the card: the editor makes every block wrapper `position: relative`, so anchoring to the card put the glyph over the title in the canvas and in the rail on the front end
- `theatrum/card-expanding` (Expanding Card) and `theatrum/card-scroll` (Scroll Reveal Card), modelled on the `expanding-card` and `gsap-card-scroll-reveal` CodePens per D-04/T3-01. Each card's **text is nested blocks** — a new `card-expanding` is seeded with `core/heading` + `core/paragraph`, a new `card-scroll` with two `core/group` sections (see below), and all of them are real blocks the author selects, edits and reorders in the canvas and List View, with a block appender for adding more. The **image is a block attribute**, chosen and sized from a shared "Card Image" / "Image Size & Fit" sidebar panel (`src/components/card-image`, the plugin's second shared inspector-control component after `arrow-controls`): a "use the post's featured image" toggle, select/replace/remove, alt text, resolution, width, height, object fit and focal point, plus aspect ratio on `card-expanding`. With the featured-image toggle on, the card draws the featured image of the post it renders — **each queried post in turn inside a Query Loop** — falling back to a separately selected image for posts that haven't got one; that is why both blocks render server-side (`render.php` + `usesContext: postId/postType`, `save()` writing only the nested blocks the way `theatrum/carousel` does) rather than from saved markup. The front-end image goes through `wp_get_attachment_image()`, so it now ships with `srcset`/`sizes` and lazy-loading; `use-card-image-preview.js` resolves the same picture from block context so the canvas matches, per card, inside a loop. Geometry is emitted as `--theatrum-card-image-*` custom properties on the `__image` element (not the block wrapper — `get_block_wrapper_attributes()` runs a merged style through `safecss_filter_attr()`), written by `theatrum_card_image_html()`/`theatrum_card_image_style()` in `inc/helpers.php` and mirrored by `get-card-image-vars.js`. `card-expanding`'s `view.js` builds the disclosure at runtime — the first heading's text moves into a real `<button>` (`<h3><button>`, the WAI-ARIA accordion shape, with `aria-expanded`/`aria-controls`; a heading already holding a link falls back to `div[role="button"]` with hand-wired keyboard activation) and the blocks below it are wrapped in the one element a height transition can animate. `card-scroll` is a fixed-height band (Height, default `12rem`) so the reveal changes horizontal layout only and nothing below the card moves while it runs — which is also why that block offers no Aspect Ratio control, and why its Height offers no `%` unit: the card has nothing for a percentage to resolve against, so one would quietly leave it sized by its content. Its text column is two sections, modelled on the "Card, detailed scroll + gallery" pattern (108052): a **Card header** group sized by its content and never scrolled, and a **Card body** group that takes the height left over and scrolls its overflow — ordinary `core/group` blocks the author owns outright, laid out by the `__header`/`__body` classes the template puts on them, with `metadata.name` labelling each in the List View. The image panel and the text column each carry the band height (`theatrum_card_height_style()`), because a flex item only stops growing with its content once it has a definite height of its own — which is also what gives the body something to scroll inside. The body is the card's **only** scroll region: `__content` is `overflow: hidden`, so a column with no `__body` in it clips at the band rather than scrolling, since a column that scrolls takes the header down with it. The sections needn't be direct children either — group them for a shared background, the way the source pattern does, and every element on the path down to `__body` becomes a pass-through flex column so the band's height still reaches it; `__header`/`__body` take `width: 100%` there because a constrained group's `margin-inline: auto !important` would otherwise switch off their stretch and shrink them to their content. Since a template only seeds newly inserted blocks and `save()`'s output is unchanged, this needed no new deprecation. Both ship a `deprecated.js` covering the three earlier shapes (v1's image/title/description attributes, v2's nested `core/image`, v3's fully static markup), migrating each into the current one; `wp db query` confirmed no live v1 instances. A deprecation only rewrites saved markup once a post is opened and saved, so `render.php` passes pre-dynamic content through untouched until then — matching the wrapper class as a whole token, since a current card's first inner block carries `{base}__header`. Each block also gained a README documenting the contract
- `theatrum/carousel` gained a Grid Gap control (`gap`/`gapUnit`, matching the existing Card Width control's pattern) — previously the gap between cards was hardcoded (`grid-gap: 24px`) with no way to change it from the editor
- `theatrum/carousel` and `theatrum/slider` share a new "Arrow Styles" inspector panel (`src/components/arrow-controls`, the plugin's first shared inspector-control component) offering arrow background on/off, arrow color, arrow background color, and arrow size — carousel's chevron changed from a fixed-color `background-image` to a CSS `mask-image` painted by `background-color` so it can actually be recolored. `theatrum/slider` also gained an Arrow Position control (outside/inside/hidden, defaulting to "inside" to preserve existing content's look); carousel already had one. Arrow backgrounds are circular in every position now (previously only carousel's "inside" position used `border-radius: 50%`)
- The `is-style-ct-carousel`/`is-style-ct-slider` formats (`core/query`/`core/gallery` styled as a carousel/slider) gained the same options as their native-block counterparts: a shared "Arrow Styles"/"Arrow Colors" panel (position, background toggle, color, background color, size), a "Carousel Layout" Grid Gap control (`core/query` only — `core/gallery` already has native gap support), and "Slider Settings" Autoplay controls (`is-style-ct-slider` previously had no autoplay mechanism at all — nothing set the `data-autoplay`/`data-autoplay-speed` attributes `src/formats/slider.js` reads). New `blocks.registerBlockType`/`editor.BlockEdit`/`editor.BlockListBlock`/`blocks.getSaveContent.extraProps` filters (`src/format-controls.js`) plus a `render_block` PHP filter for the dynamic `core/query` block (`inc/format-controls.php`, using `WP_HTML_Tag_Processor` to write the `style` attribute directly and sidestep `safecss_filter_attr()` stripping custom properties) — this plugin's first use of the core-block-extension pattern `chance-ollie`'s `ctGridColumns`/`ctGridSpan` established. `ArrowControls`/`getArrowStyleVars` gained an optional `attributePrefix` so the same components serve both native blocks (bare attribute names) and this extension (`ct`-prefixed names) without a forked duplicate

### Fixed

- Editor previews of the meta blocks drifted from what `render.php` prints on the front end, in five ways. (1) Every REST preview double-escaped `&`, `<` and `>` — the shared `theatrum_decode_entities()` decodes then re-encodes, which is correct for `inc/block-bindings.php`'s frontend output but wrong for a React text node, so "Linda & Tod White" previewed as "Linda &amp; Tod White". Added a decode-only sibling, `theatrum_decode_entities_for_preview()`, used by `inc/rest-endpoints.php` only; the frontend helper is untouched. (2) `theatrum/meta-date` and `theatrum/meta-time` hard-coded `padding: '8px 0'` on the preview element, making a `<p>` 42px tall against the front end's 26px — the onstage card pattern was already forcing `padding: 0` to hide this. (3) `theatrum/meta-related` forced `background: transparent; padding: 0` into `useBlockProps()`, so an inspector background colour or padding showed on the front end but never in the canvas. (4) `theatrum/meta-repeater`'s preview wrapper used `wp-block-theatrum-meta-repeater-preview`, a class nothing styles, instead of the front end's `repeater-rows` — so an Unordered/Ordered List block format previewed with browser-default markers and a 40px indent (live on every production with awards, via the Production Header pattern). (5) `theatrum/meta-field` put the structural `wp-block-theatrum-post-meta-field` class (which `style.scss` makes `display: inline-block`) on the inner element rather than the block wrapper, so two adjacent Meta Field blocks in a flow group sat on one line on the front end and stacked in the editor
- Five smaller editor-preview mismatches against `render.php`. `theatrum/meta-embed`'s REST fallback iframe was `width="100%" height="400" style="border:0"` where `render.php` emits `width="1200" height="675" frameborder="0"`, so the editor computed a 1:2 aspect class and the front end 16:9 — the two format strings are now byte-identical apart from the URL. `theatrum/meta-button`'s editor wrapper lacked `wp-block-button`, which all three front-end branches add. `theatrum/meta-file`'s editor fell back to "Open File" where `block.json` and `render.php` both default to "Download File". `theatrum/site-option` hard-coded `marginTop: 8px` on the list wrapper and `margin: 4px 0 0 0` / `margin: 0` on its paragraphs, overriding the theme margins the front end uses. `theatrum/meta-image`'s preview `<img>` carried `display: block`, which `render.php`'s inline `max-width:100%;height:auto;` does not, so the editor hid the descender gap visitors see
- `theatrum/meta-date`, `theatrum/meta-time` and `theatrum/meta-related` previewed as two nested elements — `<div blockProps><p class="wp-block-theatrum-meta-date">value</p></div>` — where `render.php` prints a single `<p>` carrying `get_block_wrapper_attributes()`. Every block-supports style (background, border radius, padding, colour, typography) therefore landed on the outer `div` in the editor while theme paragraph rules hit the inner `<p>`, so an inspector setting could look right on the front end and wrong in the canvas. All three now spread `blockProps` onto the single `Tag` (`attributes.tagName || 'p'`) the way `theatrum/term-meta` already did, and the inner element with its `margin: 0` / `wordBreak` inline styles is gone — `style.scss` supplies those to both views, since `block.json` points `style` at the built stylesheet the canvas also loads. `meta-related`'s `renderDisplay()` returns its children array instead of wrapping them in a second `Tag`, and the "no key entered" hint is now muted-italic via `blockProps.style` on the Tag rather than a nested `<em>`
- `theatrum/title-advanced`'s `block.json` pointed `style`/`editorStyle` at `style.scss`/`editor.scss`, which do not exist in `build/` (wp-scripts emits `style-index.css`/`index.css`), so core registered the handles with no `src` and the block's stylesheet never loaded on either the front end or the editor canvas. Repointed to the built files; the two subtitle margin resets now apply. `theatrum/query-loop` carried the same dead `editorStyle` reference to an empty `editor.scss` — removed
- `theatrum/meta-field`'s `fallbackToPostContent` option recursed infinitely whenever the block's resolved post _was_ the post holding the block, exhausting PHP's 512MB memory limit and returning a "critical error" 500. The fallback runs `apply_filters('the_content', $post->post_content)`, so rendering a synced pattern in the pattern editor (where core's `render_block()` injects the pattern's own ID as `postId` context) re-entered the same block forever. Affected the three `wp_block` patterns using the option — "Card, artist bio" (115613), "Card, artist" (115615), "Card, content + img [teaching artist]" (116495), all uneditable. `render.php` now keeps a re-entrancy guard of in-progress post IDs and skips the fallback entirely for `wp_block` posts, whose own content is never a meaningful meta value. Frontend rendering is unchanged: inside a query loop the context is the queried post, so the fallback still resolves normally
- `theatrum/slider` wasn't rendering on the frontend at all. A prior `ct-` → `tm-` class rename (commit `b081aa0`) updated the block's own markup/CSS but missed `src/formats/slider.js`/`resolve-track.js`, which still queried the old `.ct-slider-*` selectors — none matched, so the frontend JS resolved the wrong "track" element, no slide ever received `.is-active`, and the no-JS fallback CSS was disabled anyway (`.is-ready` still got added), leaving nothing visible. Same fix also corrected the "Slider Query" `is-style-ct-slider` format's arrow buttons, which were being built with the same stale class names
- `theatrum/slider`'s arrows/dots didn't respond to clicks in the block editor — `edit.js` rendered them as decorative JSX with no `onClick` handlers at all; the only click-wiring lived in the frontend-only `viewScript`. Arrow/dot clicks now call `selectBlock()` on the corresponding `slider-item` child, reusing the existing selection-driven "active slide" logic instead of adding a second, parallel state
- `theatrum/carousel`'s new arrow color/background-color attributes had no effect on the frontend despite showing correctly in the editor — `render.php` was merging them into the wrapper's `style` via `get_block_wrapper_attributes()`, which runs the combined style string through core's `safecss_filter_attr()`; that function only recognizes a fixed allowlist of known CSS properties and silently strips anything starting with `--` (custom properties). Moved the arrow vars to a raw, directly-escaped `style` attribute on the inner wrapper div instead, the same approach `cardWidth`/`gap` already used on the `<ul>` for the same reason
- `theatrum/slider`'s autoplay speed had a 1000ms floor (`RangeControl` `min`/`step`) with no way to go faster — lowered to a 100ms floor (`step={100}`); `block.json` now also documents `minimum`/`maximum` on the attribute
- A dangling `animation: ct-slider-fade` declaration (three places) referenced a `@keyframes` that had already been commented out in the same `b081aa0` commit — a deliberate fade-removal that left dead, inconsistent CSS behind rather than a live effect. Removed the leftover `animation` declarations and the fully-commented `@keyframes` block/stray comment; confirmed via grep that no `ct-slider-fade`/`tm-slider-fade` reference remains anywhere in `src/`
- A visible flash of the page background behind slider images, the first time each slide appeared (autoplay or manual arrow/dot navigation) but never again after the first pass. Two contributing causes, both fixed: (1) slide images were WordPress's default `loading="lazy"`, and a `display:none` slide's image wasn't fetched until the slide was shown — added `inc/slider-eager-images.php`, a late `the_content` filter forcing `loading="eager"` inside slider markup; (2) even with the bytes downloaded, Chromium defers _decoding_ an off-screen image into a paintable bitmap until it's revealed — `formats/slider.js` now proactively calls `img.decode()` on every slide's image(s) as soon as the slider initializes, well before any slide is shown

### Fixed

- `theatrum/page-nav` kept picking up post titles from unrelated Query Loop blocks (e.g. a "related posts" listing added somewhere in the page content) as spurious nav entries — every previous fix for this only excluded one more specific container (Tabs panels, then sections) as each new occurrence was found, which couldn't keep up with new placements. Query Loop cards (`.wp-block-post-template` items) are now only collected as nav targets when the Query Loop block itself has an HTML Anchor set (`.wp-block-query[id]`), matching how `<section>` nav targets already require an explicit HTML Anchor — a Query Loop added for some other reason is invisible to the scan by default instead of needing to be discovered and excluded after the fact
- `theatrum/meta-field`'s WYSIWYG mode (`isHtml: true`, e.g. ACF `widget_content`) rendered correctly on the frontend but showed literal escaped tags (`&lt;strong&gt;`, `&lt;em&gt;`, `&lt;a&gt;`...) in the editor preview instead of formatted HTML. Its REST endpoint (`/theatrum/v1/post-meta/{post_id}/{key}?html=1`) ran every value through `theatrum_decode_entities()`, which re-escapes `<`/`>` for safe plain-text display — correct for non-HTML fields, but it corrupted real markup before the editor's `RawHTML` preview could render it. `render.php` (frontend) never went through that function, so only the editor preview was affected. The REST callback now skips `theatrum_decode_entities()` when `html=1`, matching the frontend's `wp_kses_post(wpautop($value))` path
- `theatrum/query-filter`'s `style.scss`/`editor.scss` were never imported by its `index.js`, so wp-scripts never compiled or emitted them — the block has rendered as unstyled HTML (default browser select/button, no spacing) on every build since it was added. Added the missing imports and pointed `block.json`'s `style`/`editorStyle` fields at the compiled `style-index.css`/`index.css` output (matching every other block's convention) so the block's existing pill-style select/button CSS actually ships
- Links rendered inside custom block previews in the block editor (`theatrum/term-meta`'s resolved post links, `theatrum/meta-field` when its tag is set to `<a>`, `theatrum/breadcrumbs`' placeholder items, `theatrum/meta-file`'s file link, `theatrum/meta-related`'s linked titles, `theatrum/site-option`'s linked items, and `theatrum/meta-embed`'s raw oEmbed HTML and the `ServerSideRender`-based `theatrum/production-quotes`/`theatrum/performances-list`) could be clicked and would actually navigate the editor away from the post being edited — `theatrum/meta-button` already guarded against this with `onClick={(event) => event.preventDefault()}`; applied the same pattern (or click-delegation on the wrapper, for the two blocks whose preview is raw/server-rendered HTML) everywhere else a real `<a href>` could appear in an edit.js
- `chance/title-advanced`'s Pretitle line had no way to be customized per-page on any of the live "Header" reusable blocks (Page, Production, Venue, Event, Post, Supporter, Default) — unlike the Subtitle heading, which already used WordPress's native Pattern Overrides binding (`core/pattern-overrides`) on the Page Header block. Added the same `metadata.bindings.__default.source: "core/pattern-overrides"` to the Pretitle paragraph across all 7 live header blocks, and to Subtitle on the 6 that were missing it, so both lines are independently overridable per post. Renamed the ACF field and meta key from `pre_title` to `pretitle` (matching `subtitle`'s no-separator naming) across the ACF field group, `block-bindings.php`, `title-advanced`'s default template/`chance/post-meta` args, and existing postmeta rows
- Scoped `chance/meta-embed`'s `iframe { max-width: 100%; height: auto }` style rule to `.wp-block-chance-meta-embed iframe` — it was unscoped, and since it's registered as a block.json `"style"` (loaded in both the frontend and the block editor for every block, not just when meta-embed is present), it silently applied to any `<iframe>` on the page, including third-party block previews that render inside their own iframe
- `chance/popup` no longer uses the `hidden` attribute (which forces `display: none`) to hide its dialog/backdrop while closed — swapped for `inert`. `display: none` removes the whole subtree from the render tree, so any embedded third-party widget that measures its own size on page load (e.g. WPForms' reCAPTCHA, date pickers, or styled dropdowns) saw `0×0` dimensions and rendered broken before the popup was ever opened, even though the popup was visually hidden via `opacity: 0` regardless. `inert` blocks interaction/focus/AT-visibility the same way `hidden` did, without collapsing the box
- `chance/popup` no longer runs `wp_kses_post()` on its InnerBlocks `$content` before printing it — `$content` is already fully rendered/escaped by core's own block-rendering pipeline (no other block in this plugin re-sanitizes it), and re-filtering it against the `post` KSES allowlist stripped anything not on that list, including WPForms' inline `<script>`/`<style>` tags. KSES removes disallowed tags but can leave their text content behind as visible page text, which is what surfaced as raw JS/CSS above the form; losing the script also meant WPForms' frontend JS never ran, leaving fields stuck disabled and unstyled
- `chance/popup`'s closed backdrop/dialog (now visible-but-`opacity:0` instead of `display:none`, see above) had no explicit `pointer-events` rule, so the full-viewport `position: fixed` backdrop could still intercept clicks and hijack scroll/wheel input over the entire page even while closed and invisible — added `pointer-events: none` on both elements' closed/base state and `pointer-events: auto` only under `[data-state="open"]`, rather than relying on `inert` alone to suppress pointer interaction
- `chance/popup`'s `isOpen` was a persisted block attribute that `edit.js` wrote to on every toggle, including opening — if a post was saved (or autosaved) while a popup was open, `isOpen: true` got baked into that block's serialized JSON in `post_content`, so the editor would load it already "open" (full-canvas `pointer-events: auto` backdrop) on every subsequent visit, permanently blocking clicks/scroll in the block editor. `render.php` never read this attribute anyway (the frontend always starts closed via `view.js`), so it was pure transient UI state that never should have been persisted — removed from `block.json`, editor now tracks open/closed with local-only `useState( false )`. Existing posts with a stuck `isOpen: true` self-heal on next load since WordPress ignores attribute keys no longer declared in the block's schema
- `chance/popup`'s closed dialog/backdrop still blocked clicks and scroll in the block editor even after the `isOpen` and `pointer-events` fixes above, on a post that had never been saved with the popup open — root cause was that `style.scss`'s unconditional `.popup-dialog { display: flex }` (needed on the frontend so WPForms' JS-measured widgets still get real layout dimensions while closed) has equal-or-higher specificity than the browser's default `[hidden] { display: none }` rule, so setting the `hidden` attribute in `edit.js` never actually collapsed the box — it stayed fully laid out and centered via `position: fixed`, just invisible. Its own `pointer-events: none` didn't help either, because Gutenberg's block-wrapper styles reassert `pointer-events: auto` on the nested InnerBlocks content (e.g. the WPForms block) inside it, overriding the inherited `none`. Added an editor-only override (`editor.scss`) forcing `display: none !important` on `[hidden]`, safe there because the editor's InnerBlocks preview is always a static, disabled SSR render with no live JS-measured widgets to protect
- `chance/post-meta` block bindings source is now also registered client-side (`src/utils/meta-binding-source.js`) — WordPress core's native "Attributes" inspector panel looks the source up in the JS block bindings registry, and without a matching registration it showed "Source not registered" (disabled) and, once a value did resolve, substituted the source's raw label string into the actual block attribute (e.g. `core/image`'s `id`), which could crash the block's editor preview
- Removed the `chance/bind-embed` and `chance/bind-file` core-block-variation bindings (`core/embed`'s `url`, `core/file`'s `href`) — WordPress core's block bindings system only supports a fixed allowlist of block/attribute pairs (`get_block_bindings_supported_attributes()`), and neither `core/embed` nor `core/file` is on it, so those bindings were silently ignored everywhere (editor and front end) and never worked. Use the `chance/meta-embed` / `chance/meta-file` custom blocks instead — they don't rely on core's bindings allowlist
